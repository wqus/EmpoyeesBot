## Что исполнялось

Сквозной автоматический сценарий использует настоящий `Dispatcher.feed_update`, фильтры и middleware приложения, ORM, транзакции и отдельную PostgreSQL 16. Подменён только HTTP-транспорт Telegram. В нём сотрудник регистрируется, не допускается к раннему экзамену, проходит 10 уроков; первая попытка мини-теста даёт 3/5, пересдача 4/5; затем проходит два экзамена с 26/30 и 27/30, проверяются история и результат.

Отдельно исполнялись административные маршруты создания, изменения и удаления уроков, текста, фото, видео, документов, вопросов и отдельных вариантов, материалов/категорий, студий, переключения доступа, истории, аналитики, приглашения и отзыва роли. Изменения проверяются повторным чтением БД. Для всех 27 административных состояний проверяются блокировка посторонних кнопок, /start и очистка состояния при отмене. Для пользователей проверяются регистрация, мини-тест, неверный ввод, пересдача, два одновременных ответа и разделение состояний двух сотрудников.

Каждый DB-тест создаёт отдельную случайную схему и применяет все миграции. Предыдущий destructive fixture, удалявший все таблицы по TEST_DATABASE_URL, заменён. Проверка миграций сравнивает итоговую схему с моделями и выполняет полный downgrade/upgrade на пустых тестовых данных.

В 100 генерациях экзамена проверены 30 уникальных вопросов, охват всех 10 активных тем и различие выборок. Незавершённая попытка возобновляется через новую сессию БД. FK, UNIQUE, CHECK, rollback после flush, параллельные старты/ответы/регистрации/invite проверены на PostgreSQL.

## Границы и эксплуатационные решения

1. FSM остаётся MemoryStorage. После перезапуска незавершённые формы и мини-тест начинают заново; результаты и экзамен сохраняются в БД. Этот сценарий проверен. Несколько polling-процессов/реплик одновременно не поддерживаются; для этого потребуются общее хранилище FSM и распределённая изоляция.
2. Между PostgreSQL commit и внешним Telegram API нет распределённой транзакции. При отказе commit уже отправленное сообщение нельзя отозвать атомарно. Код восстанавливает FSM, откатывает данные и отправляет сообщение об ошибке; повтор проверен. Outbox для гарантированной доставки — отдельное расширение.
3. ProcessedUpdate растёт со временем. Автоматическое удаление истории не включено; политика хранения должна учитывать, что после очистки снова становятся выполнимы соответствующие очень старые кнопки.
4. Автоматическая отправка отчётов руководителю отсутствует по текущему поведению проекта и существующему контракту `test_exam_notifications_removed_in_favor_of_history`. Оба документа различают её с реализованной историей экзаменов. Аудит не включал незапрошенную рассылку.
5. Уровень service считает AdminCrudService доверенным внутренним API: авторизация административных действий выполняется фильтрами маршрутов; owner-only дополнительно проверяется в InviteService/handlers. Пользовательские сервисы проверяют активность сотрудника и владение попыткой. Прямой вызов AdminCrudService из нового интерфейса требует авторизации вызывающего кода.
6. Не выполнен полный статический type-check: существующий проект в значительной части не аннотирован. Исполнены compileall, проверки неопределённых имён/синтаксиса Ruff, ORM mapping/DDL, runtime-проверки и аудит установленных зависимостей.
7. Административный handler-файл остаётся крупным. Он проверен реальным выполнением маршрутов; его разбиение по предметным областям — задача сопровождения, не обязательное условие текущих исправлений.

```powershell
python -m pip install '.[dev]'
$env:TEST_DATABASE_URL='postgresql+asyncpg://USER:PASSWORD@localhost:PORT/academy_test'
python -m pytest -q --cov=app --cov-branch
python -m compileall -q app tests alembic
```

Для отдельной проверки миграций задайте `DATABASE_URL` на тестовую БД: `alembic upgrade head`, `alembic check`, `alembic downgrade base`, `alembic upgrade head`. Downgrade на БД с данными может быть ограничен историческими FK/nullable-переходами; не применять этот smoke-сценарий к рабочей БД.
